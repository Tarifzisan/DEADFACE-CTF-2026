# Don't Leave Me Hanging 

**Category:** Network Forensics  
**Challenge:** Don't Leave Me Hanging

## Summary

The provided PCAP contains VoIP traffic from Aurora Health's help desk subnet (`10.20.200.0/24`). Although most of the traffic initially appeared to be normal SIP and SRTP communication, the PBX administrator had accidentally exposed TLS session keys inside an FTP-transferred diagnostic archive.

By recovering the archive, decrypting SIP over TLS, extracting the SRTP master keys, and decoding the call audio, I identified the compromised phone as **Help Line 3 (`10.20.200.23`, extension `2003`)**.

Further investigation revealed suspicious network activity and several conversations involving Deadface-related identities. However, the exact alias requested by the challenge was not conclusively identified.

## Investigation

### 1. PCAP Triage

The capture contained approximately 256,000 packets.

The main traffic included:

- UDP/SRTP media streams
- SIP over TLS (`TCP/5061`)
- HTTPS
- SSH
- DNS
- FTP

During the initial investigation, I identified an FTP session involving:

- **Username:** `mkowalski`
- **Source:** `10.20.200.60`
- **Destination:** `10.20.200.5` (`pbx01`)
- **Downloaded file:** `pbx-diag-20261008.tar.gz`

The FTP passive data connection used port `40079`, identified from the `PASV` response (`156,143`).

### 2. Recovering the Diagnostic Archive

I reassembled the TCP stream associated with port `40079`. The reconstructed data was approximately 8,593 bytes and formed a valid gzip-compressed tar archive.

The archive contained:

```text
README.txt
messages.log
pjsip_endpoints.txt
tls-keys.log
tls-keys.log.1
```

The README revealed that `tls-keys.log` was an `SSLKEYLOGFILE` generated by the PJSIP TLS transport. The `.1` file belonged to an aborted run.

This was the critical discovery: the exposed TLS secrets could potentially decrypt the SIP signalling traffic.

### 3. Decrypting SIP over TLS

I loaded the recovered key log into Wireshark/tshark using the `tls.keylog_file` preference.

The TLS 1.3 communication over port `5061` could then be decrypted successfully.

This exposed SIP signalling, including:

- `INVITE`
- `200 OK`
- `BYE`

I identified 32 calls in total.

The SDP messages also contained SRTP crypto attributes:

```text
a=crypto:1 AES_CM_128_HMAC_SHA1_80 inline:<key>
```

Each answered call provided the necessary SRTP master material for both media directions:

- The INVITE's crypto key protected Asterisk-to-phone media.
- The 200 OK's crypto key protected phone-to-Asterisk media.

### 4. Decrypting SRTP Audio

I developed a Python-based SRTP decryption script.

The implementation performed the following operations:

1. Extracted the inline SRTP master key and salt.
2. Split the 30-byte master material into the master key and master salt.
3. Derived the session encryption, authentication, and salt keys using the AES-CM key derivation labels (`0`, `1`, and `2`).
4. Constructed the packet IV using the SSRC and RTP packet index.
5. Decrypted the SRTP payload using AES Counter Mode.

I extracted both directions of each answered call and reconstructed 28 calls as WAV files.

The resulting audio streams decoded correctly, confirming that the recovered SRTP keys were valid.

### 5. Analysing the Call Audio

I used Whisper (`small.en` through sherpa-onnx) to transcribe the recovered conversations.

Several interesting findings emerged.

**Inband DTMF — Call `06826701`**

The tones represented three-digit decimal ASCII codes.

Decoding them produced:

```text
deadface{Pr355_0n3_f0r_D34df4c3}
```

Although this resembles a valid flag, it did not appear to be the requested alias. I treated it as a possible side result or decoy.

**RFC 4733 DTMF**

Another call contained the following digits:

```text
40917#
```

Its meaning remains unknown.

**Hold Music**

Two calls contained only hold music:

```text
145f8b32
80ea2c07
```

These recordings may contain additional information that has not yet been investigated.

**Speech Analysis**

Most calls involving Help Line 3 appeared to be staged complaints about IT support being rude or hanging up.

However, one conversation contained particularly interesting references.

### 6. Identifying Suspicious Network Activity

After identifying Help Line 3 (`10.20.200.23`), I correlated its network activity with the recovered conversations.

The host communicated with suspicious infrastructure:

| Domain | Resolved IP |
|---|---|
| `ghosttown.deadface.io` | `165.22.177.32` |
| `maudeai.deadface` | `203.0.113.66` |

Requests used the following custom User-Agent:

```text
SunstalkerDFBrower/2.0 (Linux; Android 14)
```

The host also generated several DuckDuckGo searches in this order:

1. `Deadface ghosttown`
2. `Hiding things in plain sight`
3. `Blondie songs`
4. `Is Maude rotting my brain`
5. `Maude.md file examples`

No other host in the capture contacted the identified Deadface infrastructure.

These observations further strengthened the suspicion surrounding `10.20.200.23`.

### 7. Analysing the Key Conversation

One particularly interesting conversation was recovered from call `d2d8f47d`.

**Caller ID:** Maureen Casey  
**Destination:** Help Line 3

The conversation contained the following statements:

- Caller: "It's Lamia... you know Sunstalker?"
- Agent: "Good for her."
- Agent: "Right now I'm doing something important for Spooky Boy."

These references suggest connections between the insider and multiple Deadface-related identities.

However, the dialogue alone does not establish which alias belongs to the insider.

## Unresolved Questions

Several leads remain unexplored:

- Approximately 20 calls involving Help Lines 1, 2, 4, and the remaining Help Line 3 conversations still need transcription.
- The meaning of the RFC 4733 sequence `40917#` is unknown.
- The searches for "Blondie songs" and "Hiding things in plain sight" may indicate a steganographic clue.
- The `Maude.md` references may point to additional hidden information.
- The two hold-music recordings may contain concealed data or messages.

## Conclusion

The investigation successfully uncovered an exposed TLS key log, decrypted the SIP signalling, recovered SRTP media keys, and reconstructed the VoIP conversations.

The strongest evidence points to **Help Line 3 (`10.20.200.23`, extension `2003`)** as the compromised endpoint.

However, the exact Deadface alias associated with the insider remains unresolved. Further transcription and analysis of the remaining calls are necessary before submitting a definitive flag.
